## Prepare

You need:

- Node.js 22.22 or later in the 22.x line, or Node.js 24 or later, with npm and Bash.
- A Cloudflare account with the Workers Paid plan and R2 active. Password hashing exceeds the CPU limit of the Free plan. Check [Workers](https://developers.cloudflare.com/workers/platform/pricing/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [R2](https://developers.cloudflare.com/r2/pricing/), and [Durable Objects](https://developers.cloudflare.com/durable-objects/platform/pricing/) pricing.
- A password manager for the generated credentials.

Run these commands from the checkout root. Use one shell for all steps.

```sh
npm ci
unset CLOUDFLARE_ENV
export WRANGLER_LOG_SANITIZE=true WRANGLER_WRITE_LOGS=false WRANGLER_SEND_METRICS=false
npx wrangler login     # only if whoami shows no login
npx wrangler whoami    # must list the intended account
```

Never put provider tokens in arguments, files, or bug reports.

Copy the example settings and set your values. Use new names that no other deployment uses.

```sh
mkdir -p .wrangler/installation
cp src/server/adapters/cloudflare/tooling/provision.example.jsonc .wrangler/installation/provision.jsonc
cp src/server/adapters/cloudflare/tooling/provider.example.json .wrangler/installation/provider.json
cp src/server/adapters/cloudflare/tooling/site.example.json .wrangler/installation/site.json

MINSKY_INSTALL_ACCOUNT_ID='REPLACE_WITH_ACCOUNT_ID'
MINSKY_INSTALL_DATABASE='my-contest-database'
MINSKY_INSTALL_BUCKET='my-contest-images'
MINSKY_INSTALL_ORIGIN='https://my-contest-app.ACCOUNT_SUBDOMAIN.workers.dev'
MINSKY_INSTALL_CONFIG="$PWD/.wrangler/installation/wrangler.jsonc"
```

Set `account_id` in `provision.jsonc`. The account subdomain is in the dashboard's Workers settings.

## 1. Create the database

Confirm the account first. The output must show the account whose ID you set in `provision.jsonc`. If it does not, stop and correct `account_id`.

```sh
npx wrangler whoami --config=.wrangler/installation/provision.jsonc
```

Then create the database:

```sh
npx wrangler d1 create "$MINSKY_INSTALL_DATABASE" --config=.wrangler/installation/provision.jsonc --update-config=false
MINSKY_INSTALL_DATABASE_ID='REPLACE_WITH_NEW_DATABASE_UUID'
npx wrangler d1 info "$MINSKY_INSTALL_DATABASE" --config=.wrangler/installation/provision.jsonc --json
```

To choose a region, add `--location=apac` or another [location hint](https://developers.cloudflare.com/d1/configuration/data-location/#provide-a-location-hint). A hint is not a guarantee.

## 2. Plan and configure

Fill in `provider.json`. It holds public values only.

| Field | Value |
| --- | --- |
| `accountId` | Your account ID |
| `workerName` | The new Worker name in the origin, for example `my-contest-app` |
| `databaseName`, `databaseId` | From step 1 |
| `bucketName` | `$MINSKY_INSTALL_BUCKET` |
| `origin` | `$MINSKY_INSTALL_ORIGIN`, no trailing slash |
| `placementRegion` | Optional. A [placement region](https://developers.cloudflare.com/workers/configuration/placement/#specify-a-cloud-region) near D1, for example `aws:ap-southeast-1`. Omit it to use Smart Placement. Set this value. In one hosted test in October 2026, Smart Placement ran the Worker in North America against a D1 database in Asia Pacific, with a median request of 1,537 ms and scenario timeouts. An explicit region near the database gave 125 ms. |

```sh
npm run cloudflare:install -- plan --settings=.wrangler/installation/provider.json --config="$MINSKY_INSTALL_CONFIG"
npm run cloudflare:install -- configure --settings=.wrangler/installation/provider.json --config="$MINSKY_INSTALL_CONFIG"
```

`plan` prints `"status": "plan_only"` and the target. Check it.
`configure` writes the Wrangler configuration and never overwrites a file.
Do not edit the generated file. To change settings, generate a new one at a new path.

## 3. Create the image bucket

```sh
npx wrangler r2 bucket create "$MINSKY_INSTALL_BUCKET" --config="$MINSKY_INSTALL_CONFIG" --update-config=false
```

Keep the bucket private. Do not add an `r2.dev` URL or a public domain. The Worker serves images to authorized users.

## 4. Migrate

```sh
npm run cloudflare:install -- migrate --config="$MINSKY_INSTALL_CONFIG" --account="$MINSKY_INSTALL_ACCOUNT_ID" --database="$MINSKY_INSTALL_DATABASE_ID"
```

## 5. Build and deploy

Before the real deploy, check in the Cloudflare dashboard that no Worker has your `workerName`. Never replace an existing Worker.

```sh
npm run build
npx wrangler deploy --config="$MINSKY_INSTALL_CONFIG" --dry-run
npx wrangler deploy --config="$MINSKY_INSTALL_CONFIG"
```

## 6. Create the first webmaster

Bootstrap creates exactly one webmaster and nothing else. It makes no event, contest, or team.
The command reaches your hosted D1 database only. It has no local mode, so run it with the Cloudflare login of the installation.

In `site.json`, set `webmasterName` and `webmasterHandle`.
A handle has 3 to 32 lowercase letters, digits, `_`, or `-`, and starts with a letter or digit.

```sh
MINSKY_INSTALL_PRIVATE_DIR="$(mktemp -d)" && chmod 700 "$MINSKY_INSTALL_PRIVATE_DIR"
npm run cloudflare:install -- bootstrap --config="$MINSKY_INSTALL_CONFIG" --account="$MINSKY_INSTALL_ACCOUNT_ID" --database="$MINSKY_INSTALL_DATABASE_ID" --site=.wrangler/installation/site.json --credentials="$MINSKY_INSTALL_PRIVATE_DIR/webmaster.json"
```

`webmaster.json` has mode `0600`. It holds the webmaster's account ID, handle, and temporary password. Move it to your password manager. Never commit or share it.
Bootstrap is atomic and refuses a database that already has data.

## 7. Enable sign-in

```sh
npm run cloudflare:install -- secret --config="$MINSKY_INSTALL_CONFIG" --account="$MINSKY_INSTALL_ACCOUNT_ID" --database="$MINSKY_INSTALL_DATABASE_ID"
```

This command sets a random `AUTH_SECRET` without printing it. It refuses to replace an existing secret.

## 8. Verify

1. Open your origin, select **Sign in**, and select **Site sign-in**.
2. Enter the handle and the temporary password from `webmaster.json`, and change the password.
3. Check that the **Site** page opens and shows "No events yet."
4. Check that a private path returns `404`:
   ```sh
   curl -s -o /dev/null -w '%{http_code}\n' "$MINSKY_INSTALL_ORIGIN/.env"
   ```
5. Run the [complete journey](/operators/verification/) on a fictional event.

Record the source revision, the Worker version, the resource IDs, and the results.

To start real work, [create an event](/guides/webmaster/#create-an-event).

## If something fails

The installer prints a fixed message and hides provider output. It never deletes resources.

| Problem | Do this |
| --- | --- |
| Settings or target rejected | Fix `provider.json` or the login. Configure again at a new path. |
| R2 error `10042` | Activate R2. Check whether the bucket exists before you retry. |
| Migration fails | Inspect the applied migrations. Do not reset the database or rerun bootstrap. |
| Secret fails | Check that the Worker exists. The command never rotates an existing `AUTH_SECRET`. |
| Bootstrap fails or its output is lost | Keep any result file. Check for a webmaster with the query below. If one exists, [recover the password](#recover-a-webmaster-password). |
| Output file exists | Keep it. Choose a new path. Minsky never overwrites these files. |

To check whether bootstrap committed, run this query. It shows IDs only.

```sh
npx wrangler d1 execute "$MINSKY_INSTALL_DATABASE" --remote --config="$MINSKY_INSTALL_CONFIG" --command="SELECT account_id FROM grants WHERE scope = 'site'"
```

## Repair an event deletion

A webmaster deletes an event on the **Site** page. See [Delete an event permanently](/guides/webmaster/#delete-an-event-permanently). The Worker then deletes its rows and its live state. About 65 minutes later, it deletes its files. This section is for the operator when a deletion does not finish.

**Stopped** on the **Site** page means that an account of the event also has activity in another event. Deleting that account would change the other event, so Minsky keeps it. The event stays closed. Its contests are already gone. The accounts that Minsky has not reached, all of the event's files, and its live updates stay until the deletion continues. Minsky tries again every hour, and it continues when the other event no longer names the account, for example after that event's own deletion. Do not delete rows by hand, except in the case that follows.

Two deletions can stop each other for good. This happens when two old account operations that name no contest run in both directions between an account of each event. Neither event's deletion can remove the operation that its own account performed on the other event's account. If two events show **Stopped** and each names an account of the other event, remove those operations. Both events are going, so no record that stays changes.

1. Find the two event IDs. Use the database name that you chose earlier.

	```sh
	npx wrangler d1 execute "$MINSKY_INSTALL_DATABASE" --remote --config="$MINSKY_INSTALL_CONFIG" --command="SELECT event_id, event_name FROM event_deletions WHERE blocked IS NOT NULL"
	```

2. Delete the operations between the accounts of those two events. Replace `EVENT_A` and `EVENT_B` with the IDs.

	```sh
	npx wrangler d1 execute "$MINSKY_INSTALL_DATABASE" --remote --config="$MINSKY_INSTALL_CONFIG" --command="DELETE FROM account_operations WHERE session_id IS NULL AND actor IN (SELECT id FROM accounts WHERE event_id IN ('EVENT_A', 'EVENT_B')) AND account_id IN (SELECT id FROM accounts WHERE event_id IN ('EVENT_A', 'EVENT_B'))"
	```

	Expect both deletions to continue at their next hourly try.

The Worker logs each failed attempt as `deletion.advance_failed`, with the `eventId`, a `phase`, a `cause`, and the error's name, and it retries every minute. The line holds fixed words and IDs. It never holds an error's text, because that text can hold a person's data.

| Field | Value | Meaning |
| --- | --- | --- |
| `phase` | `contests` | D1 refused a delete under a contest. |
| `phase` | `accounts` | D1 refused a batch of accounts. |
| `phase` | `event` | D1 refused the last batch, which deletes the `events` row. |
| `phase` | `live` | A Durable Object erase failed. |
| `phase` | `files` | An R2 list or delete failed. |
| `phase` | `unknown` | D1 also refused the read that finds the phase. |
| `cause` | `foreign_key` | D1 says that a foreign key refused the write. A row outside the event names a row of the event. |
| `cause` | `internal` | D1 gives no reason. A provider failure looks like this. A foreign key that fails when a batch commits can also look like this. |
| `cause` | `other` | Any other error. |

If the **Site** page shows no progress for an event:

1. Watch the log. Replace `WORKER_NAME` with the name of your Worker.

	```sh
	npx wrangler tail WORKER_NAME --config="$MINSKY_INSTALL_CONFIG" --format json | grep deletion.advance_failed
	```

	Expect one line each minute for a deletion that keeps failing, and no line otherwise.
2. Compare `eventId` with the event, and check the D1 and R2 status of your Cloudflare account. A provider failure clears by itself, and the deletion continues from its current step.
3. If the same line stays after the provider recovers, keep the event's journal and report `phase`, `cause`, `errorName`, and `errorCode` to the maintainers. A foreign key refusal stays until someone changes the row that holds the key, and **Stopped** does not appear for it when D1 hides the reason. Do not change `event_deletions` or `event_deletion_targets`, because each later step reads them.

## Recover a webmaster password

Use this procedure when a webmaster cannot sign in and no other webmaster can help.
If another webmaster can sign in, that webmaster can [reset the password on the **Site** page](/guides/webmaster/#manage-webmasters) instead.
For an event admin, a contest admin, or a contestant, an organizer [issues a new password in the app](/guides/event-admin/#share-passwords-and-print-sheets).

You need these items:

- A private, interactive terminal on your own computer. The command refuses CI. It also refuses a terminal whose output is redirected, because the password must stay on that screen.
- A Wrangler login for the Cloudflare account of the installation.
- The configuration file from step 2. Another Wrangler file works if it has exactly one `DB` binding with `"remote": true` and no `env` section. Without `--config`, the command reads `wrangler.jsonc` in the checkout, which has no remote database, and refuses.
- The webmaster's handle.

The command changes the database that the file names, and it asks for no confirmation. Check `database_name` in the file before you run it.

1. From the checkout root, run the command. Separate each flag from its value with a space. The command refuses the `--flag=value` form.
   ```sh
   npm run cloudflare:recover-admin -- --config "$MINSKY_INSTALL_CONFIG" --username WEBMASTER_HANDLE
   ```
2. Confirm that the first line of the output names your database: `Recovering a webmaster in remote D1 database <name>.`
3. Copy the temporary password from the terminal. The command prints it once and writes it to no file or log. Do not paste the output into chat or commit it.
4. Give the password to the webmaster through a secure channel.
5. The webmaster signs in with **Site sign-in** and must change the password.

The command makes these changes in one database batch:

- It sets a new temporary password and requires a password change at the next sign-in.
- It ends every login and session of the account.
- It records the recovery in `authority_audit` and in `account_operations`.

The account keeps its ID and history.

The command refuses an unknown handle, a disabled account, and an account that is not a webmaster. It does not re-enable a disabled account or restore a removed webmaster.
If the batch fails, the old password stays valid. Run the command again.
